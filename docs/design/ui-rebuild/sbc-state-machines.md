# SBC fork: transport and state machines

Basis: pocket-dial `main` at `a26afa65` (2026-10-08), read-only. `origin/main` was de61ba14 (45 commits ahead, not fetched); the headline findings were re-checked there with `git grep`. 3CX facts are from the official 3cx.com docs fetched 2026-10-16. Anything the docs do not state is marked UNCONFIRMED. All `file:line` cites are at `a26afa65`. Paths under `src/SIP` unless noted.

## 1. Transport, confirmed

Owner's belief: "WebSocket for state control, raw PCM over HTTPS for media."

| Claim | Verdict | Evidence |
|---|---|---|
| There is no encrypted SIP tunnel; 3CX is reached over an API, not SIP | Right | `TelephonyProvider.hpp:15-20`: "OAuth2 client-credentials, a call-control WebSocket, and chunked-HTTPS PCM16 media streams". Token POST `TelephonyAnchorClient.cpp:969` (`/connect/token`). A repo-wide grep for `tunnel` finds zero hits, so the repo cannot say anything about 3CX's own SBC tunnel. |
| WebSocket for state control | Half right. The WS is receive-only. | `wss://{host}/callcontrol/ws` (`TelephonyAnchorClient.cpp:1151-1162`), Bearer header on the upgrade (:1164-1175). The grep `esp_websocket_client_send` over `src/` and `main/` returns zero hits. |
| (continued) where control actually goes | Every command and state read is an HTTPS REST call | makecall `/callcontrol/{dn}/devices/{id}/makecall`, legacy fallback `/callcontrol/{dn}/makecall` on 404 (:393-461); answer `.../participants/{id}/answer` (:764); drop `.../participants/{id}/drop` (:719); reads `GET .../participants` (:1402) and `GET .../devices` (:1706). |
| (continued) the docs | The docs say the WS can also carry requests | `docs/3cxAPI+Webhooks.md:81-92`, and the 3CX Call Control page. pocket-dial does not use this. The 3CX page also calls the WS an "event-only channel" with a message-size limit and no number. The docs are internally in tension. |
| Raw PCM over HTTPS for media | Right, with a correction | Two separate chunked-HTTPS streams per call, each on its own TLS connection, both on `.../participants/{id}/stream`: POST upload (:3267, `application/octet-stream`, :3296) and GET download (:3505). Not one channel. No RTP, no WS audio, no SIP on the carrier side. |
| Format | PCM16 little-endian, 8 kHz, mono | Code: `int16_t` LE (:3833-3838), 320-sample chunks (`MediaBridge.hpp:207`). 3CX docs: "PCM 16-bit 8000Hz mono", roughly 128 kbps, post "with minimal jitter". The 8 kHz rate is inferred in the repo (µ-law decoded with no resampler, `MediaBridge.cpp:181`, `PlayoutBuffer.hpp:15`); the 3CX docs state it. |
| Who opens the connection | The board, as a client | GET opens at ringing, retries on 404 or 424 (:3521-3536); POST opens at answer or at pre-warm. No inbound NAT problem. Retry budget is 240 attempts (about 2 min). |

Other corrections to carry forward:
- **Auth.** OAuth2 client-credentials, token cached as `"Bearer " + token` (:1013). The code takes lifetime from the JWT `exp - iat` with a 50-minute fallback (:124, :130-172) and says the OAuth `expires_in` of 60 s is wrong. The 3CX docs say `expires_in: 3600` and "all tokens expire after one hour". These two records disagree; see open question 3.
- **Token refresh blocks while media is live** (:1076-1095) because 3CX invalidates the old token when a new one is issued.
- **Event types.** Code: 0 Upsert, 1 Remove, 2 DTMF, 3 PromptDone (declared at :117, no handler). Docs list 0, 1, 2, 4 (Response), and one page also says "EventType=5". Minor mismatch.
- **Event gating.** Frames are admitted only if the entity path is exactly `/callcontrol/{dn}/participants/{id}` (`TelephonyAnchorLogic.hpp:184-194`) and `dn == _sourceDn` (:2925). Any extension-status or presence entity, and any other DN, is discarded today. This gate is the first thing the fork has to change.
- **`isConnected()` is the WS flag only** (:327-330). A WS drop calls `stopAllMediaStreams()` (:2865), so one drop ends every call's media.
- **Not behaviour, don't cite:** ADR-002 (`IAnchorProvider`, AudioSocket framing, `mute()`/`dtmf()`), `ApidazeAnchorClient` (stub), and the "real mTLS" comment at :72 (the code is Bearer plus `crt_bundle_attach`, :1176).
- **Verification record.** Two-way outbound PSTN audio was seen once on the bench (2026-09-13, `CHANGELOG.md:1021-1034`). That is the best inference for the 3CX path, not an explicit statement. Against it, the #518 comment (:3659-3665) records every GET stream answering 403 for all 240 attempts on .244, and `CHANGELOG.md:356` says the GET stream is unproven on a live tenant. No entry found says #518 was resolved. Report both; do not say "the media path is verified".
- **3CX side of /stream.** Docs do not say which participants allow `/stream`. Community reports (unofficial) say RoutePoint legs only, which would fit the #518 403s. UNCONFIRMED.
- **Licensing.** Docs say an 8SC+ license is required for Call Control and XAPI, and Programmable Extensions needs V20 Update 10.

## 3. Order of work

Size reasoning is mine, derived from the inventory; no estimates were measured.

**Small (poll or event feed, then reuse the existing NOTIFY emitter)**
1. **Relax the WS entity gate** (`TelephonyAnchorLogic.hpp:184-194`, `TelephonyAnchorClient.cpp:2925`) so monitored DNs other than `_sourceDn` are parsed, without changing the call path for `_sourceDn`. Prerequisite for A.
2. **Machine A, remote BLF.** A fixed array of remote DN to state token, fed from WS events, seeded and resynced by `GET /callcontrol` on connect. The BLF code then ORs this overlay with session-derived state (`BlfSubscriptions.cpp:62-104`). The NOTIFY emitter, expiry, and 489/404/503 refusals are reused. Gate before building: confirm on a live tenant that the WS delivers events for additional monitored DNs and what `status` values appear.
3. **Fix the stale `online` flag** and the stale comment at `RequestsHandler.cpp:1226-1229`. Small, independent, already identified.

**Large**
4. **Machine B, profile status.** Blocked on the API question, not on code. If a live probe finds a status field, it still needs a shared extension-status owner, DND persistence, and DND honoured on groups, hunt, page and anchor ring-all.
5. **Machine E, survivability policy.** Needs a decision on what stays up with the link down (the WS drop currently kills all media), a link-health model beyond `isConnected()`, and tests. No test covers BLF expiry sweep or the 503 pool-full path today.
6. **Machine D gaps** (hold, #518 GET 403). The 403 may be a 3CX-side limit on which participants allow `/stream`; that is unconfirmed.
7. **Machine C, remote MWI.** Not startable without an API; no work until open question 2 is answered.

**Must stay out of the firmware's packet path (rules: no heap after init, `tick()` at 1 Hz)**
- Keep every HTTPS call (token, `GET /callcontrol`, any XAPI poll) in the anchor client's existing task, never inside SIP packet handling or the engine's `_mutex` section. Today the engine holds one `_mutex` across the BLF, registrar, DND and forward machines. The packet path should only read pre-filled fixed arrays.
- New state is fixed-size arrays (like the 16 BLF slots, 32 MWI boxes), sized and failing closed like the existing 503/drop cases. No growth at runtime.
- Polling is slow, on the order of the 1 Hz `tick()` or slower, and rate-limited. 3CX documents no rate limits, which is not the same as none (UNCONFIRMED).
- Do not refresh the token while any media stream is live (:1076-1095). Any poller that needs a fresh token competes with this.
- Memory pool check: `POCKETDIAL_MSG_POOL=8` in the constrained build (`main/CMakeLists.txt:276`) versus `MAX_SUBSCRIPTIONS`=16 contradicts the "must stay <= MSG_POOL" comment at `PoolConfig.hpp:50-53`. Resolve before adding remote subscribers.

## 4. Open questions

1. Does the WS deliver Upsert/Remove for monitored DNs other than the Service Principal's own DN, and with which participant `status` values? (Docs: values not enumerated.) How are idle and "no participants" represented?
2. Is there any readable or settable profile status, forwarding profile or voicemail count in the live `/xapi/v1/$metadata`? The public docs answer none of it. One probe on a real tenant settles B and C.
3. Real token lifetime: docs say 3600 s, `TelephonyAnchorClient.cpp:120-142` says 60 s from OAuth is wrong and uses JWT `exp - iat`. Which governs the Call Control credential? (The docs' Call Control pages did not name a token endpoint.)
4. Does the "See Presence" right (https://www.3cx.com/docs/manual/rights-recordings/) apply to the API view of another user's state?
5. Why does `/stream` GET return 403 (#518)? Does it only work on RoutePoint legs? Is the 09-13 two-way audio on the anchor path or not?
6. What should local phones do when the 3CX link is down: keep local calls, show remote BLFs as unknown or idle, queue nothing? (Policy, decision for the owner.)
7. Does a remote-state overlay own DND, forwards and BLF tokens, or does a separate extension-status record own them? Decide before B.
8. Does 3CX support a third-party SBC in its extension dropdown? Docs say nothing; its SBC list is 3CX-provisioned. UNCONFIRMED, and relevant if the fork presents itself as an SBC.
9. The 4-call concurrency claim and inbound-from-carrier calls are not recorded as hardware-verified (comments only).
